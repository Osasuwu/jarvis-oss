Multi-Agent Orchestration Pattern Comparison

Project: Jarvis (solo-developer AI agent system) · Date: 2026-05-20 · Status: RESOLVED — pass 2 + 2.5 evidence complete; direction decided in a /reason session (see §0). Pass 3 (C4+C5 deep dive) cancelled — the resolution removed its premise. Document retained as a reusable research base for future agentic-system decisions.

0. Final Resolution (2026-05-20)

The half-day substrate debate (federation → C4-supervisor-as-core → …) collapsed back to where the project's own jarvis-build-vs-buy memo already stood. The deciding move was reframing the question, not filling more matrix cells.

The deciding cut — true vs mimic always-on. A persistent resident process is only required by genuine always-on work: (1) reaction within seconds, (2) continuous stream-watching to catch anomalies in the moment, (3) real-time co-authoring where the reply lands before the user finishes typing. None of Jarvis's real tasks fall there. Everything that looked like it needed an always-on agent (news/info gathering, vulnerability scanning, goal & resource & user-state tracking, pattern finding, time-window analysis) needs neither instant reaction nor continuous observation — it dissolves into a durable task queue + goal-aware prioritization running on a reactive substrate.

Key distinction: persistent behaviour ≠ persistent process. A cron/event-woken agent that reads accumulated state and drains a priority queue looks always-on to the user, with none of the cost or failure modes (no host-restart problem, no unproven 24/7 substrate, no cross-device checkpoint contamination, ~free).

Four decisions recorded:

  1. Substrate = reactive event-driven (native Claude Code) + durable task queue + goal-aware prioritization. No resident always-on process. (decision episode 38816c8d)
  2. LangGraph is NOT the orchestrator engine. Routing → the woken session does it natively via the Agent tool; HITL → Telegram + queue; multi-wake plan checkpoint → a Supabase table. LangGraph as an optional plan-checkpoint MCP is still contested, not a locked carve-out — possibly not needed at all. (episode aec88add; reverses the Sprint-1 “LangGraph persistent agents are the path” line)
  3. Federation (C5) deferred. Owner-originated, unproven, no solo precedent; revisit only after the reactive core ships and proves insufficient. The orchestrator-worker-inside-a-task half survives (a woken orchestrator dispatching isolated subagents IS supervisor+subagents — the isolation reviewers valued holds, just without LangGraph as the engine). (episode 55a5c1a8)
  4. The “no custom scripts/services” prohibition is relaxed to native-first priority (not a ban); custom code permitted on merit. Conscious reversal of a 4-day-old rule, on principle — not because this design forces custom code (it barely does). (episode d9be0390)

Anti-confirmation note (this is the point of the exercise). The evidence walked the decision away from both priors: the owner expected long-lived federation to win; the reviewer majority (Никита/Илья) favoured a LangGraph supervisor + subagents. The end-state — reactive-native core, LangGraph optional/minimal, federation deferred — matched neither. The owner's authorship of the federation idea was deliberately hidden from the neutral-researcher dispatches so the evidence would not be graded sympathetically.

Why this document is kept. When a separate agentic system gets built (e.g. for the company/campaign), this is a ready research base — 7 patterns, 11 weighted criteria, the failure-mode evidence, and the matrix — making it faster to pick the right shape for that problem, which may legitimately differ from Jarvis's.

1. Reading Guide

Cell tags

  • [strong] — primary sources: production post-mortems, official architecture docs, peer-reviewed papers, direct source-code reading.
  • [weak] — secondary sources: blogs, tutorials, vendor marketing.
  • DISQUALIFIED — documented insurmountable failure on a MUST criterion. The row stays visible so reasoning is auditable.
  • no evidence — no citable source was findable. Different from “the pattern fails” — the question is open. See structural concerns for why some cells lack evidence.

How to use this matrix

  1. The matrix does not pick a winner. The neutral researcher fills cells from primary sources; the operator and reviewer decide.
  2. MUST criteria are veto-strength — DISQUALIFIED on any MUST removes the candidate from consideration regardless of NICE performance.
  3. NICE criteria break ties between candidates that survive MUST.
  4. A column with many [weak] cells does not automatically mean the pattern is weaker — it may mean the pattern is under-studied. Pass-2 researcher flagged this asymmetry explicitly in Structural Concerns §5.
  5. Cells that quote different units (e.g. per-event latency vs end-to-end latency) are not directly comparable. See Structural Concerns §4.

What the “Dispatcher's Honest Read” section is for

The operator's synthesis is shown separately from the matrix, at the bottom, so a reviewer can ignore it and work directly off the evidence if preferred. The synthesis is explicitly marked as opinion, not neutral findings.

2. What's Being Decided

Jarvis needs a long-lived agent architecture that:

  • Coordinates between multiple input sources (GitHub issues, Telegram, calendar, cron, world-events).
  • Dispatches coding work to Claude Code worker subagents.
  • Maintains state and goals across sessions and across 3 physical devices (Workshop PC, Main PC, Laptop) connected by Tailscale and a shared Supabase database.
  • Presents a single conversational surface to the solo operator regardless of which internal agent handles the request.

The 2026-04-22 design memo (federated_architecture_direction) committed to a HYBRID pattern: federation across jurisdictions + orchestrator-worker inside a delegated task. A May 2026 design re-discussion temporarily proposed collapsing that into a single always-on local-LLM orchestrator. This research process pressure-tests both — and several alternatives — against weighted criteria. Pass 1 surfaced the alternatives; pass 2 (the matrix below) compares them.

3. Research Process

3-pass neutral research, each pass dispatched to a general-purpose subagent without the operator's framing or preferences:

  • Pass 1 — Enumeration. “Enumerate persistent multi-agent / orchestration patterns in 2024-2026 production and academic literature; document trade-offs and failure modes per pattern. Do not rank.” Surfaced 12 pattern families.
  • Pass 2 — Weighted comparison (this matrix). Narrow to 7 candidates; evaluate against 11 weighted criteria; cite per cell; flag contested/gaps/structural concerns.
  • Pass 2.5 — Two missing axes (HITL gate placement + host-restart recovery) flagged by the pass-2 researcher; narrow re-dispatch in progress.
  • Pass 3 — Deep dive on the chosen direction(s) (to be locked after the operator + reviewer read this document). Will produce mechanism-level recommendations for the grill phase.

Pass-2.5 Contested Cells

  • C3 / X1 (HITL): Third-party summary (centific.com) says “Checkpointing enables human-in-the-loop workflows: the agent pauses for approval, persists state, resumes when authorized” [weak — third-party]. This contradicts the primary Anthropic source, which makes no such claim. The safer reading: secondary source generalises HITL-via-checkpointing patterns; it does not describe Anthropic's specific system.
  • C4 / X1 (granularity inside supervisor): post_model_hook description (“Useful for implementing human-in-the-loop”) implies HITL at supervisor's routing decision, not only inside workers. Whether this is “first-class” or “convention-via-hook” is interpretively contested.
  • C7 / X2 (replay completeness): paper's “reconstruct read-model exactly” addresses deterministic projection from a complete log. It does not address what happens if orchestrator crashes between accepting an intention and appending the event — a classic two-phase-commit gap.

Pass-2.5 Gaps

  • C3 cross-device: Anthropic article gives no info on whether the multi-agent research system can migrate a live lead process between machines. Memory persistence necessary but not sufficient.
  • C3 HITL: no primary-source production HITL placement. Any insertion is bolt-on.
  • C4 RemoteGraph + interrupt: known open issue (langgraph#4879). Relevant if C4 deployed with workers in separate processes (which a 3-device setup may require). In-process supervisor+workers case is unaffected.
  • C5 entire row: no primary source. All claims derive from prompt definition + analogue frameworks. Cannot be cited [strong].
  • C7 entire row on operational properties: paper is academic, covers semantics not operations.
  • Time-to-resume: undocumented for all 4 patterns.
  • Duplicate-work risk: explicitly addressed only for C4; inferred for the others.

Pass-2.5 Structural Concerns

  1. X1 conflates “pattern supports HITL” with “pattern names a canonical HITL gate.” C4 and C7 both can support HITL at multiple insertion points, but in C4 the gate is named (interrupt(), post_model_hook) while in C7 it would be ad-hoc validator. Treating these as equivalent obscures design-cost difference. Conversely, C3 and C5 lack canonical gates for opposite reasons (C3: nothing in docs; C5: pattern definition names one specific gate — cross-jurisdiction conflict).
  2. X1 mixes “where can a human approve” with “how is the human notified.” Sync vs async approval depends on whether host blocks or persists-and-resumes — that property is a consequence of X2's persistence story, not independent. The axes are correlated, not orthogonal.
  3. X2 conflates three distinct properties: (a) state survives a crash on the same machine (trivial with any DB), (b) a fresh process can resume from persisted state (requires no machine-local caches or in-memory queues at decision points), (c) a different physical machine can take over (requires shared storage URI, no host-specific paths in state, idempotent effects). C4's PostgresSaver is documented for (a)+(b)+(c); C3 has evidence for (a)+(b) but not (c); C7 has (a)+(b) by construction but paper is silent on (c); C5 depends entirely on jurisdiction implementation. Reporting them as a single “host-restart recovery” score flattens a real distinction.

10. Structural Concerns with the Question

Raised by the pass-2 researcher; not recommendations, just methodological warnings the reviewer should weigh.

  1. C5 is under-specified for external comparison. The label exists in project memory but does not match a single arxiv paper or named industry framework. To compare it head-to-head with peer-reviewed candidates, one either (a) cites the project's federated_architecture_direction as the spec (asymmetric — others have papers), or (b) decomposes it into mechanistic claims (long-lived processes + shared DB + dedicated user-facing jurisdiction + ephemeral coding workers) and compares each. The current matrix takes path (a), which mechanically inflates no evidence cells for C5 — honest but not a defect of the pattern itself.
  2. M2 and N1 overlap when “Claude Max subscription” is the cost envelope. Model flexibility (M2) ranks against cost only if paid API is substituted for subscription-bundled Claude. If the envelope is “Claude Max + ≤$20 external”, then a pattern that only runs on hosted Claude (no Ollama path) is cheaper on N1 than one requiring local-only. The two criteria pull in opposite directions for this user.
  3. M3 (Real-work suitability) conflates two questions: (a) has this exact pattern shipped coding-work product? (b) is the pattern capable of shipping coding work? The matrix answers (a) — unfair to C5 (project-internal) and C7 (n=2). If the question is (b), every candidate could plausibly ship coding work given engineering effort; the criterion no longer discriminates.
  4. M5 (Latency floor) needs a definition of “useful action”. Sub-second per-event (C7) vs minutes-to-result (C3) are not comparable units; C3 is end-to-end, C7 is per-event overhead. Without a common task definition the cell values are not commensurable.
  5. MAST taxonomy is not applied symmetrically. MAST (arxiv 2503.13657) explicitly studied C3/C4-shaped architectures and a blackboard-adjacent topology. It did not study C2, C5, or C7. The “M4 — Failure modes” comparison therefore advantages patterns not in MAST (fewer documented failures = appears safer). A pattern with fewer documented failures may simply be under-studied, not more robust.
  6. Missing axis: HITL gate placement. Several candidates differ in where a human can interject (per-event for C7, per-subagent-result for C3, per-blackboard-iteration for C6, per-loop-iteration for C1). The current criterion set treats HITL only as “M1 — does not require it”. An axis “where can HITL be cleanly inserted without architectural surgery?” would discriminate the candidates more cleanly and matches the dispatcher's solo-developer-with-tiebreaker model. (Pass 2.5 addresses this.)
  7. Missing axis: state-recovery cost after host-machine restart. N3 touches this but blurs it with multi-device interactive access. Solo-dev on 3 devices specifically needs “host process dies on machine A, can I resume from machine B?” — this is C7's strongest evidence and C1's weakest, but doesn't surface cleanly in current rows.
