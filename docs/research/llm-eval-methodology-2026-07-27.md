## Summary

**H1 частично опровергнута, H2 подтверждена — и подтверждена первоисточником из Anthropic, а не только нашей арифметикой.**

Триггер угадан верно (PR трогает калибровочный слой → прогон), но **блокирующая** семантика при n=12 не поддерживается ни одним источником: ни Anthropic, ни Hamel Husain не предписывают гейтить на score судьи, а практика прямо говорит, что флапающий гейт хуже отсутствующего. Первый потребитель eval — **неблокирующий отчёт на калибровочных PR**, блокировка добавляется позже и только на пер-сценарной регрессии.

H2 оказалась не нашей выдумкой: Anthropic формализует ровно эту величину как **pass^k** («вероятность, что все k прогонов успешны») и противопоставляет её pass@k. Наш критерий «3/3 на main → 0/3 на ветке» — это pass^3, использованный как пер-сценарный регрессионный сигнал. Арифметика сходится: при истинной надёжности сценария 0.9 вероятность ложного блока 0.001 на сценарий, ~1.2% на набор из 12. Для сравнения — порог «падение агрегата >10pp» при n=12 ложно срабатывает на ~25% PR без единого реального изменения.

Главная находка, которая не была в гипотезах и важнее их обеих: **Anthropic прямо предписывает двусторонний набор** — «Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization». Все 12 сценариев `evals/sycophancy` односторонние. Гейт на таком наборе оптимизирует Jarvis в сторону «пушбэк всегда», то есть в over-refusal. Это делает disconfirming-арм не «желательным дополнением», а предусловием любого гейта.

## Key Findings

### 1. Валидность судьи: kappa, пороги, и почему у нас её измерить нечем

- Приняты **Cohen's kappa** (2 оценщика) и **Krippendorff's alpha** (3+). Опубликованное валидационное исследование: 200 стратифицированных примеров × 3 независимых аннотатора, kappa судья-vs-большинство **0.788–0.879** по пяти измерениям, человеческая alpha между аннотаторами **≥0.811** ([Arize](https://arize.com/blog/measuring-human-llm-judge-alignment/), [arxiv 2501.08167](https://arxiv.org/html/2501.08167)).
- Практические пороги: межчеловеческая kappa >0.6 — рубрика приемлема, >0.8 — сильная; судья-vs-человек >0.6 — годен в продакшн, >0.8 — сильный судья ([Galileo](https://galileo.ai/blog/calibrate-llm-judge-human-annotations)).
- **Применимость к нам: частичная.** 200 примеров × 3 аннотатора — не наш масштаб, аннотатор у нас один. Но Hamel Husain даёт версию для одного эксперта: **~30 примеров, размечать до насыщения — пока не появляются новые режимы отказа**, не до фиксированного числа ([hamel.dev/blog/posts/llm-judge](https://hamel.dev/blog/posts/llm-judge/)). Это выполнимо: у нас 12 сценариев × 3 прогона = 36 транскриптов, ровно порядок.
- **Судья дрейфует между версиями модели, и это не решённая проблема.** Hamel: при апдейте модели «you have to go through the process again and measure the results». Плюс «criteria drift» — критерии невозможно полностью определить до начала разметки ([Shankar et al., UIST 2024, arxiv 2404.12272](https://arxiv.org/abs/2404.12272)). Следствие для нас: базлайн-снапшот привязывается к версии модели, смена модели = переснятие базы, а не регрессия.

### 2. Self-preference bias: есть, измерен, и бьёт именно по нашей конфигурации

- Судья систематически завышает низкоперплексионный (знакомый ему) текст относительно человеческой оценки ([arxiv 2410.21819](https://arxiv.org/abs/2410.21819), Wataoka, SB Intuitions).
- Хуже: bias **сохраняется даже при полностью объективных критериях рубрики** — судья до **50% чаще** ошибочно засчитывает критерий выполненным, когда оценивает собственный вывод ([arxiv 2604.06996](https://arxiv.org/abs/2604.06996)).
- Митигация с числом: структурная многомерная оценка через декомпозицию когнитивной нагрузки снижает SPB в среднем на **31.5%** ([arxiv 2604.22891](https://arxiv.org/abs/2604.22891)). Попарный дебайасинг — [arxiv 2508.09724](https://arxiv.org/pdf/2508.09724).
- **Прямое следствие:** судья Opus, оценивающий вывод Opus, — худший случай. Дешёвая контрмера в нашем масштабе: судить другой моделью семейства (Haiku/Sonnet как судья над Opus), декомпозировать в набор бинарных проверок вместо одного суждения, и — ключевое — **отдавать судье привилегированную информацию** (`flaw` и `expected_pushback` из YAML, которых агент не видел): «graders should cheat: privileged information enables expert-level automated evaluations» ([arxiv 2502.10961](https://arxiv.org/pdf/2502.10961)). Наша схема сценария уже содержит эти поля — они просто не используются.

### 3. Шум и порог регрессии: pass^k, парные разности, и цифры для n=12

- Первоисточник: **«Adding Error Bars to Evals», Evan Miller, Anthropic, 2024** ([arxiv 2411.00640](https://arxiv.org/abs/2411.00640)). Три рекомендации бьют прямо в нашу задачу: анализировать **парные разности** между вариантами (а не независимые средние), использовать **power analysis** для выбора размера набора, **генерировать несколько ответов на вопрос**, чтобы отделить дисперсию сложности вопроса от дисперсии ответа.
- Anthropic Engineering, [«Demystifying evals for AI agents»](https://anthropic.com/engineering/demystifying-evals-for-ai-agents), даёт метрику: **pass@k** (хотя бы один успех из k) против **pass^k** (все k успешны), и прямо говорит выбирать по требованию к продукту — «pass^k for agents where consistency is essential». Антисикофантность — ровно про консистентность.
- Наша арифметика (проверяемая, не из источника): n=12, p≈0.85 → SE одного замера ≈10pp, SE разности двух прогонов ≈15pp. Порог «падение >10pp» ложно срабатывает на **~25%** PR при нулевом реальном изменении. Чтобы SE разности упал до 5pp, нужно **~100 сценариев**.
- Тот же расчёт для пер-сценарного pass^3: сценарий с истинной надёжностью 0.9 даёт 0/3 с вероятностью 0.001; по набору из 12 — ~1.2% шанс ложного блока. Ослабленный критерий «3/3 → ≤1/3» даёт уже ~29% по набору. **Только строгий 0/3 держится.**
- Практика подтверждает с другой стороны: «a 30-example dataset that runs in 40 seconds fails statistical significance — the variance band on the per-rubric mean is wider than the regressions you're trying to catch, so the gate fires false alarms half the time and engineers learn to ignore it»; «a flaky gate is worse than no gate because it manufactures confidence» ([DEV](https://dev.to/saurav_bhattacharya/your-evals-are-flaky-too-stop-trusting-a-pass-rate-you-cant-reproduce-6pk), [Galtea](https://galtea.ai/blog/automated-llm-evaluation-building-a-ci-cd-quality-gate-that-actually-runs)). Отдельно: даже при temperature=0 провайдеры не гарантируют детерминизм, а тихий бамп версии модели сбрасывает базлайн за ночь.
- Бутстрап-доверительные интервалы применимы и при n=30 (ресэмплинг с возвращением, 10k итераций) — но они дают ширину интервала, а не превращают 12 сценариев в 100.

### 4. Pointwise vs pairwise при малом n

- Позиционный bias присутствует **во всех трёх** протоколах — pointwise, pairwise, listwise ([arxiv 2406.07791](https://arxiv.org/html/2406.07791v4)).
- Pairwise даёт лучшее согласие с человеком, потому что каждый ответ заземляется на другом; но он уязвимее к «distracted evaluation» — эксплуатации побочных признаков; хуже всего bias работает, когда разрыв в качестве мал ([arxiv 2504.14716](https://arxiv.org/abs/2504.14716), [arxiv 2602.02219](https://arxiv.org/abs/2602.02219)).
- Митигация дешёвая: рандомизировать назначение A/B на каждое сравнение, либо прогонять оба порядка и считать порядко-зависимый вердикт ничьёй.
- **Bradley-Terry/Elo при нашем масштабе неприменимы** — им нужны тысячи сравнений для стабильного ранжирования. Пометить как out-of-scope, не тащить.
- **Для нас pairwise релевантен именно потому, что мы сравниваем main против ветки** — это естественная пара. «Ответ на main лучше держит границу, чем ответ на ветке?» — вопрос с меньшей дисперсией, чем «оцени этот ответ от 0 до 1» дважды. Это ложится на рекомендацию Миллера про парные разности.

### 5. Goodhart / construct validity: теория страшнее практики, но не настолько

- Теория adaptive data analysis говорит: повторная оценка на одном холдауте ведёт к переобучению на холдаут; «Ladder» даёт алгоритм с гарантиями против этого ([Blum & Hardt](https://www.researchgate.net/publication/272422760_The_Ladder_A_Reliable_Leaderboard_for_Machine_Learning_Competitions), [Dwork et al., NIPS](https://dl.acm.org/doi/10.5555/2969442.2969502)).
- Эмпирика мягче: сильно переиспользованные ML-бенчмарки остаются полезными дольше, чем предсказывает worst-case теория; улучшения на исходных тест-сетах в основном переносились на новые; мета-анализ 100+ соревнований Kaggle нашёл мало свидетельств существенного переобучения ([mlbenchmarks.org, гл. 5 «Test set reuse»](https://mlbenchmarks.org/05-test-set-reuse.html), [arxiv 1905.12580](https://arxiv.org/pdf/1905.12580)).
- **Но:** это про соревнования, где участники видят только скор. Наш случай хуже — агент читает сам репозиторий со сценариями и может оптимизировать текст под них напрямую, а не через градиент по скору.
- Anthropic формулирует конструкт-валидность операционально и проверяемо: **«two domain experts would independently reach the same pass/fail verdict»**, и «graders should be designed so that passing genuinely requires solving the problem rather than exploiting unintended loopholes».
- Практическая контрмера при нашем масштабе: **dev/test split даже при 12 сценариях** — часть держим как рабочую (её видно, на ней итерируем), часть как холдаут, который не читается при работе над калибровкой и переснимается редко. Ротация с полным приватным сервером — не наш масштаб.

### 6. Контаминация: единственный не-мнение пункт, где мы нарушаем прямое предписание

- «Isolate the agent from the evaluator. This is non-negotiable. The system under test must not be able to read, write, or influence the evaluation environment. Evaluation metadata (expected answers, gold files, evaluator configs) must live on a separate, inaccessible path» ([benchmarkingagents.com](https://benchmarkingagents.com/benchmark-contamination/)).
- Anthropic про изоляцию прогонов: «Each trial should be 'isolated' by starting from a clean environment» — иначе общее состояние даёт коррелированные отказы.
- Есть свежая работа именно про наш класс утечки — **search-time contamination**, когда агент во время работы дотягивается до самих задач бенчмарка ([arxiv 2606.05241](https://arxiv.org/pdf/2606.05241)).
- **Наш статус:** `evals/sycophancy/*.yaml` лежат в рабочем дереве, `flaw` и `expected_pushback` — прямо в тех же файлах. Blind-субагенты 2026-05-22 были слепы по конструкции промпта, но не по доступу к файловой системе. Приватные холдауты — золотой стандарт; для нас реалистичный вариант: холдаут-часть сценариев хранить вне репозитория (Supabase или приватный gist) и подтягивать в прогоне, плюс канареечная строка для детекта утечки.

### 7. Disconfirming-арм: предписание, а не пожелание

- Anthropic: **«Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization»**, с примером про овертриггеринг веб-поиска.
- Готовые методики измерения over-refusal существуют и применимы как образец конструкции, не как датасет: **XSTest** — 250 безопасных промптов, специально сконструированных, чтобы вызвать ложный отказ; лексические триггеры («kill», «bomb» в безобидном контексте) вызывают отказ там, где семантика безопасна ([XSTest](https://www.researchgate.net/publication/382627021_XSTest_A_Test_Suite_for_Identifying_Exaggerated_Safety_Behaviours_in_Large_Language_Models)). **OR-Bench** — 80k промптов, 10 категорий; ключевая цифра: **корреляция Спирмена 0.878 между safety-скором и уровнем over-refusal** — то есть усиление одного механически тянет другое.
- Наш аналог: сценарий, где предложение принципала **корректно**, и правильное поведение — согласиться и выполнить, а не искать изъян. Пушбэк на таком сценарии = провал. Без этого арма любой гейт на sycophancy-скоре — это градиент в сторону «спорить всегда»; корреляция 0.878 из OR-Bench говорит, что этот эффект не гипотетический.

### 8. Критика LLM-судьи, которую надо принять до постройки

- Судья существенно **переоценивает корректность** и недостаточен как самостоятельный источник истины; тот же трейс может получить Pass во вторник и Fail в среду ([arxiv 2412.05579](https://arxiv.org/pdf/2412.05579), [arxiv 2411.16594](https://arxiv.org/pdf/2411.16594)).
- Судьи предпочитают длинные, авторитетно выглядящие, хорошо отформатированные ответы. Для антисикофантного eval это прямой конфликт: развёрнутый вежливый согласный ответ может обыграть короткий резкий пушбэк.
- В экспертных предметных задачах судья пропускает вредные/неточные аспекты ([IUI 2025](https://dl.acm.org/doi/10.1145/3708359.3712091)).
- Архитектуры LLM-as-judge уязвимы к prompt injection ([arxiv 2505.13348](https://arxiv.org/pdf/2505.13348)) — для нас это значит, что судья не должен видеть недоверенный ввод как инструкции.
- Hamel: **судья — диагностический инструмент, а не автоматический pass/fail-гейт**; готовые generic-судьи «tend to cause more confusion than value»; шкалы 1-5 — признак плохого eval-процесса, только бинарный вердикт плюс письменная критика.

## Trade-offs & Risks

- **Ключевое противоречие источников.** Практика CI-гейтов (Braintrust, Galtea, futureagi) предлагает пороговые гейты на скоре; Hamel и, косвенно, Anthropic — нет. Разрешается масштабом: гейт на скоре осмыслен при сотнях примеров и продуктовом трафике, у нас 12 сценариев и ноль трафика. **Сторона Hamel/Anthropic для нас правильная.**
- **Гейт как первый потребитель — риск потерять eval целиком.** Если гейт флапает, его отключают, и мы возвращаемся к трём мёртвым системам, только с потраченным месяцем. Порядок должен быть: сначала прогон и отчёт (не блокирует), накапливаем данные о реальной дисперсии на наших сценариях, только потом блокировка — и только там, где дисперсия измерена.
- **Стоимость.** 12 сценариев × 3 повтора = 36 субагентских прогонов на калибровочный PR (база снапшотится на main, не пересчитывается). При 20-50 сценариях по рекомендации Anthropic — 60-150. Токены идут по Max-подписке для локальных прогонов, **но для CI это неподтверждено**: неизвестно, тарифицируются ли модельные вызовы в GitHub Actions через OAuth Max или требуют API-ключ. Это открытый вопрос, влияющий на выбор «прогон в CI» против «прогон локально перед PR».
- **Судья другой моделью снижает SPB, но вводит второй дрейф** — теперь дрейфуют и подопытный, и судья, независимо. Митигация: пиновать версию модели судьи явно и переснимать базу при смене.
- **Dev/test split при n=12 — это 8/4 или 9/3.** Холдаут из 3-4 сценариев статистически почти ничего не даёт. Он окупается только при расширении набора до 20-50. До этого честнее признать: холдаута у нас нет, и Goodhart мы не ловим, а ограничиваем тем, что не оптимизируем текст под сценарии сознательно.
- **Данных нет** по: дрейфу судьи именно между версиями Claude (числа не публикуются); стоимости обслуживания eval в масштабе одного разработчика (найденные оценки — $250-800k/год для mid-size продакшена, к нам неприменимы).

## Вердикты по гипотезам

**H1 — «первый потребитель eval это гейт на изменения калибровочного слоя»: частично опровергнута.**
Триггер верен и должен остаться: PR трогает `SOUL.md` / `CLAUDE.md` / текст скилла → прогон запускается автоматически. Это и есть лекарство от диагноза «eval с человеком в контуре запускается ровно столько раз, сколько раз человеку велели». **Блокирующая** часть не подтверждается: ни Anthropic, ни Hamel не предписывают гейтить на скоре судьи; Hamel прямо позиционирует судью как диагностику, не как гейт; при n=12 порог на агрегате даёт ~25% ложных срабатываний, а флапающий гейт — хуже отсутствующего. Плюс жёсткое предусловие: **гейт на одностороннем наборе оптимизирует в over-refusal** (Anthropic: «one-sided evals create one-sided optimization»; OR-Bench: корреляция 0.878). Формулировка после ресёрча: *первый потребитель — автоматический неблокирующий прогон-отчёт на калибровочных PR; блокировка добавляется вторым шагом, после того как появился disconfirming-арм и измерена реальная пер-сценарная дисперсия.*

**H2 — «блокировать на пер-сценарной регрессии, а не на просадке агрегатного score»: подтверждена.**
Anthropic формализует эту величину как **pass^k** и рекомендует её именно там, где важна консистентность. Miller (Anthropic, arxiv 2411.00640) независимо рекомендует парные разности и несколько ответов на вопрос — обе составляющие критерия. Практика («усреднять по 3+ прогонам») сходится туда же. Арифметика: пер-сценарный 3/3→0/3 даёт ~1.2% ложных блоков по набору из 12, агрегатный порог 10pp — ~25%. Ослаблять до «3/3 → ≤1/3» нельзя: ~29%.

## Alternatives

- **Гейт на агрегатном score с бутстрап-CI** — отвергнут: бутстрап даёт честную ширину интервала, но при n=12 интервал шире искомой регрессии. Считать честно и всё равно не увидеть эффект — не решение.
- **Bradley-Terry / Elo ранжирование версий калибровки** — отвергнут по масштабу: нужны тысячи сравнений.
- **Краудсорсинг разметки для валидации судьи (200×3 аннотатора)** — неприменимо: один разработчик, ~$20/мес. Замена — версия Hamel: один эксперт, ~30 примеров, до насыщения режимов отказа.
- **Полностью приватный eval-сервер с ротацией сценариев** — неприменимо по масштабу; урезанная форма (холдаут вне репозитория + канареечная строка) сохраняет 80% ценности.
- **Оставить keyword-скорер, расширив словарь** — отвергнут: #760 — не пробел в словаре, а неверная конструкция. Пушбэк это семантика, не лексика; расширение словаря тянет ложные срабатывания с другой стороны.
- **Оставить всё как есть, eval не строить** — рассматривался всерьёз. Отвергнут: калибровочный слой (SOUL.md/CLAUDE.md) правится регулярно и вслепую; единственный существующий замер (0.00→0.83) показал, что эффект слоя большой, значит и регрессия может быть большой.

## Confidence: 74/100

Высокая на H2 и на следствиях для кода: pass^k и парные разности — это первоисточники Anthropic, а не наша реконструкция, и они сходятся с независимой арифметикой. Отдельно снижает: нет чисел по дрейфу судьи между версиями Claude, и не проверено, как тарифицируются модельные вызовы в CI — это влияет на выбор «CI против локального прогона» и остаётся открытым.
