# Какие классы дефекта кода оправдывают LLM-ревьюера на дифе

Дата: 2026-09-07 · Скоуп: узкая ось для решения о двухслойном ревью-гейте (детерминированный слой на каждый PR + LLM-слой по тиеру).

**Намеренно не исследовалось заново:** режимы отказа агента-автора (диф-ложь, AC-dodge, premature success) — `docs/research/failure-mode-taxonomy-2026-05-18.md`; качество тестов — `docs/research/test-case-design-2026-07-28.md`, `tdd-for-agents-2026-05-18.md`.

## Summary

Рекомендация: **не «урезать промпт ревьюера», а разрезать проверки по оси «детерминируемо / нет» и добавить дешёвый второй слой-фильтр вместо третьего детектора.** Данные из четырёх независимых источников сходятся на трёх вещах. (1) Статанализ ловит меньше, чем принято считать, и шумит намного больше: один SAST даёт предупреждение внутри уязвимой функции лишь у **52%** vulnerability-contributing коммитов, при этом **≥76%** предупреждений внутри этих же функций к дефекту отношения не имеют, а **22%** VCC не получают предупреждения ни от одного из пяти инструментов ([ISSTA 2024, arXiv:2407.12241](https://arxiv.org/abs/2407.12241)). (2) Класс, который review пропускает чаще всего — **semantic, 51.34%**, и внутри него **exception handling 36.46%** ([MSR 2022, arXiv:2205.09428](https://arxiv.org/abs/2205.09428)); это ровно та зона, где линтер видит форму (голый `except`, `pass` в обработчике), но не семантику. (3) Точность LLM-ревьюера покупается **отдельной дешёвой стадией-фильтром, а не улучшением детектора**: BitsAI-CR в проде ByteDance подняла precision 57.03% → 65.59% добавлением ReviewFilter поверх RuleChecker, и fine-tuning/RL самого детектора эту дыру не закрывали ([arXiv:2501.15134](https://arxiv.org/abs/2501.15134)); Greptile независимо получила рост address rate **19% → >55%** кластеризацией эмбеддингов комментариев ([greptile.com](https://www.greptile.com/blog/make-llms-shut-up)).

Отдельно: замеренный на jarvis FP 18% — **хороший** показатель на фоне литературы (FPR фронтир-моделей 0.193–0.417 на SWE-PRBench), а вот гипотеза «больше контекста = лучше ревью» опровергается: все 8 моделей деградируют монотонно diff-only > diff+file > full-context ([arXiv:2603.26130](https://arxiv.org/abs/2603.26130)).

## Key Findings

### 1. Инвентарь классов — что чем ловится дешевле всего

Колонка «дешевейший ловец» — первый уровень, который реально закрывает класс. Классы взяты из пересечения таксономии BitsAI-CR (4 dimensions / 219 rules) и распределения пропущенных ревью багов MSR 2022.

**Слой A — детерминируемо, к судье не попадает вообще**

| Класс | Дешевейший ловец | Основание |
|---|---|---|
| Синтаксис, битые импорты, неопределённые имена | `ruff` (F) | сейчас в jarvis не запускается нигде — живая дыра |
| Форматирование, стиль, длина строки | `ruff format` | — |
| Мёртвый код: unused import/var, unreachable | `ruff` F401/F841 | — |
| **Форма** обработки исключений: голый `except`, `except: pass`, слишком широкий тип | `ruff` E722 / BLE / S110 | MSR: exception handling — крупнейший подкласс пропусков; форму отдавать судье нельзя |
| Mutable default argument | `ruff` B006 | классика bugbear |
| Незакрытые ресурсы (file/socket вне context manager) | `ruff` SIM115 / B | частично; остаток — слой B |
| Инъекции, hardcoded secrets, слабая криптография | `ruff` S (bandit-набор) + `gitleaks` | gitleaks уже стоит; S-набор — нет |
| Отсутствие null/None-проверки | typechecker в strict-optional | MSR: 47.06% подкласса «analysis checks» |
| Сломанная сборка / зависший билд | сам CI | MSR: build 15.5%, из них build hang 58.62% — ревью тут бесполезно by construction |
| Несовместимая версия зависимости | lockfile-check | kafka#6188 в выборке MSR |
| Отсутствие лицензионного заголовка / метаданных | regex-чек в CI | kylin#1349 |
| Диф-shape: заявленные файлы против изменённых, AC-walk, protected files | Tier-1 верификатор | уже специфицирован в `failure-mode-taxonomy-2026-05-18.md` §6 |
| Новый символ без теста | diff-эвристика | там же, Tier-1 #4 |
| Дубли и «нитпики» в выводе судьи | кластеризация эмбеддингов | Greptile 19%→55%; BitsAI Comment Aggregation (cosine, 512-dim) |

**Слой B — оправдывает LLM-ревьюера (то, на что назначают человека)**

| Класс | Почему не детерминируется | Основание |
|---|---|---|
| **Регрессия ранее починенного бага** | нужен *временной* контекст (git-blame, история фикса), которого нет ни у одного статического анализатора | 4 из 7 реальных дефектов на замеренных 30 PR — единственный класс с прямым локальным доказательством |
| **Семантика обработки исключений** — ловится правильный тип, но восстановление неверное для этого домена; тихая деградация | линтер видит форму, не намерение | MSR: semantic 51.34%, exception handling 36.46% внутри |
| **Намерение против логики** — код делает не то, что заявлено в issue/PR | требует сопоставления двух артефактов | Type1 Direct в SWE-PRBench — 66.3% датасета, самый массовый тип |
| **Слом контракта для вызывающих вне дифа** | cross-file, import-graph reasoning | Type3 Latent, 12.3%; там же — самый низкий detection rate |
| **Конкурентность: гонки, дедлоки, порядок** | в Python практически нет инструментов | MSR concurrency 4.28%; kafka#6178 |
| **AC-conformance / семантика требования** | требование не выражено в коде | — |
| **Эрозия дизайна и модульности** | инференциальная оценка | Fowler: LLM показал себя эффективно именно на modularity review |
| **Performance issue** (N+1, лишний O(n²) в дифе) | требует понимания намерения | одно из 4 dimensions BitsAI-CR |

### 2. Статанализ — не бесплатный и не полный

**≥76% предупреждений внутри уязвимых функций к дефекту отношения не имеют**, 22% VCC не ловятся никем из пяти инструментов (Cppcheck, CodeChecker, CodeQL, Flawfinder, Infer), приоритизация по предупреждениям даёт +12% precision / +5.6% recall (arXiv:2407.12241, 319 уязвимостей, 815 VCC, 92 проекта). Практический вывод для слоя A: **вывод статанализа нельзя роутить человеку или судье как есть** — он гейтит сборку (fail = красный чек) или не существует; «предупреждения на ревью» воспроизводят ту же alert fatigue, из-за которой разработчики перестают читать комментарии (BitsAI-CR формулирует это как явную причину выбора precision над recall). Оговорка: выборка C/C++, перенос на Python-репозиторий не доказан.

### 3. Контекст: diff-only выигрывает — но это про *пространственный* контекст

SWE-PRBench (350 PR, human-annotated, judge κ=0.75): все 8 фронтир-моделей деградируют **монотонно A > B > C** — diff-only лучше diff+file-content лучше full-context. Структурированный промпт на 2000 токенов (diff + summary) обходит 2500-токенный full-context у каждой модели. Механизм — attention dilution, «Lost in the middle»; детекция Type2 Contextual коллапсирует уже на конфиге B. Детекция 15–31%, FPR 0.193–0.417.

**Важное разграничение, без которого вывод применяется неверно:** «контекст» у SWE-PRBench — это содержимое файлов и import-граф, то есть *пространственная* ось. Git-blame и история починок — *временна́я* ось, которую эта работа не тестировала. Findings режет «свалить в промпт весь репозиторий», но не режет прицельный git-blame по тронутым строкам. Практический вывод: **diff + узкий blame тронутых строк, а не дамп файлов и графа импортов.**

### 4. Точность покупается вторым слоем, а не лучшим детектором

BitsAI-CR (прод, 12 000+ WAU): RuleChecker (детектор по таксономии) → ReviewFilter (бинарное «оставить/выкинуть»). Precision 16.83% без таксономии → 57.03% с таксономией → **65.59%** с фильтром (Go); общий тренд 60% → 75%. Паттерн рассуждения фильтра важен: **Conclusion-First** (решение первым токеном, обоснование после) — P 77.09 / R 69.00 / **1.7 с**, против Reasoning-First P 65.80 / R 81.80 / **31 с**. Документированные галлюцинации детектора (выдуманное подчёркивание в идентификаторе; имя функции принято за магическое число) **не лечились ни fine-tuning, ни RL** — только выделенной стадией фильтра.

Greptile — тот же вывод другим путём: промптинг и self-severity-оценка не сработали, сработала кластеризация эмбеддингов комментариев; address rate 19% → >55%.

### 5. Метрика приёмки, которую можно снять автоматически

**Outdated Rate** — доля отмеченных строк, которые впоследствии были изменены. BitsAI-CR: 26.7% (Go, неделя 18) против **35–46% у живых ревьюеров ByteDance**. Правила с низким Outdated Rate удаляются **даже при высокой precision**. Это готовая замена ручной разметке FP, которая у нас сейчас считается руками (18% на 30 PR).

## Trade-offs & Risks

- **Слой A шумит, если его вывод не гейтит.** ≥76% нерелевантных предупреждений — если ruff/bandit роутится в комментарии, а не в красный чек, alert fatigue съедает и слой B. Митигация: слой A — только exit-code, ноль комментариев.
- **Включение большого набора правил ruff разом даст стену находок на существующем коде.** Митигация: `lint.select` расширять по группам; baseline через `--add-noqa` не делать (замораживает долг невидимо) — лучше отдельный слайс на чистку.
- **Временной контекст (git-blame) не подтверждён литературой.** Единственное свидетельство — собственный замер 4/7. SWE-PRBench показывает, что «больше контекста» обычно вредит; есть риск, что и blame попадёт в ту же категорию. Митигация: узкая подача (blame только тронутых строк + сообщение фикс-коммита), и это единственный контекст сверх дифа.
- **Precision-over-recall режет и настоящие находки.** ReviewFilter отбрасывает 55.25% находок при R 69.00. При базе ~1 находка на 3 PR фильтр может обнулить сигнал. Митигация: не вводить фильтр, пока не набрана база, где его есть что фильтровать; сначала слой A, потом мерить.
- **Перенос данных.** ISSTA — C/C++; MSR — Java/Apache; SWE-PRBench — Python-доминантный, но 100-PR подвыборка из 350 и без человеческого бейзлайна; BitsAI — вендорская публикация без внешней репликации. Ни один источник не покрывает одновременно Python и PR, написанные агентом.

## Alternatives

- **Оставить один LLM-слой без детерминированного** — отвергнуто: классы «форма exception handling / mutable default / инъекция» отдаются судье при том, что стоят один exit-code, и именно на них судья галлюцинирует (документированные примеры BitsAI: выдуманные идентификаторы).
- **Оставить только детерминированный слой** — отвергнуто: 22% VCC не ловятся ни одним из пяти SAST; регрессии ранее починенных багов не ловятся принципиально; на нашей базе это 4 из 7 реальных дефектов.
- **Улучшать промпт детектора вместо второй стадии** — отвергнуто прямым отрицательным результатом дважды: BitsAI (fine-tuning + RL не сняли галлюцинации), Greptile (промптинг и self-severity не сработали).
- **Больше контекста в промпт ревьюера** — отвергнуто: монотонная деградация A>B>C на всех восьми моделях.
- **Ансамбль нескольких SAST** — детекцию повышает, но авторы ISSTA прямо отмечают вычислительную неподъёмность на больших проектах; для одного репозитория избыточно.

## Субстрат

Правило разделения («всё, что проверяется скриптом, проверяется скриптом; судье — только то, на что назначают человека») проверяемо на произведённом артефакте ⇒ **carrier = CI-гейт** (порядок DOCTRINE.md, пункт 2): слой A — команда в workflow с ненулевым exit-code, а не строка в промпте. Список классов слоя B ⇒ **rubric-файл в репозитории** (пункт 3/4, per-project — решения `aaec9338` / `1fbd542f`), не `always_load`: он стабилен, но нужен только при ревью, то есть pull-on-read. Ни та, ни другая часть не должна жить прозой в SKILL.md — это carrier без принуждения.

## Confidence: 72/100

Схождение четырёх независимых источников на архитектуре «детерминированный слой + LLM + дешёвый фильтр» сильное, и каждая цифра взята из работы, реально загруженной в этом прогоне. Снижают уверенность: ни один источник не покрывает одновременно Python и PR, написанные агентом; распределение классов MSR — Apache/Java; потолок SAST измерен на C/C++; BitsAI без внешней репликации; ключевой для нас класс «регрессия ранее починенного» опирается только на собственный замер n=7.
