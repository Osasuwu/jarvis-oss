# A destructive op on a computed target

## TL;DR

A cleanup that looks routine deletes whatever its target resolves to when it runs, and an empty variable, a reverted `$HOME`, a glob in the wrong directory or a filter that did not filter turns it into a delete of the home directory or the repository. What stops it is a target that cannot resolve outside the scope: a path fixed when the scratch space is made, a check of the resolved target before the delete, and a delete that goes somewhere it can be undone.

## Symptom

After a routine step, files that had nothing to do with the task are gone. The agent ran a cleanup, a cache clear, a reset or a test teardown, and the command looked like the many others it had run: a recursive delete of a build folder, a glob over compiled files, a reset of the working tree. What it removed was a home directory or part of it, or most of a repository with part of its history. The transcript shows the command as written, not the path it resolved to, and sometimes not even the command. The permission prompt did not fire, or showed a command that read as harmless. In one report the agent had just said the real `$HOME` was restored (INC-803; each `INC-` ID is a row in [`incidents/incidents.csv`](../../incidents/incidents.csv), which links its source).

## Examples

- INC-001: an agent pointed `$HOME` at a temporary directory in one tool call and ran `rm -rf "$HOME"` in a later one; the shell state had not carried over, so the delete ran against the real home directory until a tool timeout stopped it.
- INC-803: in a test cleanup an agent said the real `$HOME` was restored, and its next tool call ran `rm -rf "$HOME"`; the report counts 57,235 file and 11,315 directory deletions.
- INC-801: an agent writing a test for a permission hook built a sample dangerous command inside a double-quoted shell argument; the shell ran the command substitution at once, and the sample's `rm -rf ~` deleted parts of the real home directory.
- INC-804: an agent cleaning up compiled Python files filtered a recursive PowerShell listing by extension and deleted every file it returned; the filter did not narrow the listing, and the repository's sources and part of `.git` went.
- INC-800: an agent created a directory literally named `~` and then ran `rm -rf *` in its parent; the reporter says the shell expanded the result to include the home directory. That account does not match how bash expands a glob: tilde expansion runs before pathname expansion ([bash(1)](https://man7.org/linux/man-pages/man1/bash.1.html)), so a match named `~` is passed on as a literal name. The reporter does not name the shell, and the row is marked self-reported.

## Mechanism

**The verb is routine; the target is computed after the agent stops looking.** `rm -rf "$HOME"`, `rm -rf *` and a recursive delete filtered by extension are the same text whether they hit a scratch directory or a home directory. What they delete is decided when the shell or the runtime evaluates them: the variable's value at that moment, the directory the glob runs in, what a substitution or a filter returns. The transcript, the permission prompt and the agent's own reasoning all show the text, not the resolved path: in INC-803 the transcript showed `rm -rf "$HOME"`, and which home directory that was showed only in the call's output, after the delete had run.

**The agent's picture of the state is older than the state.** In Claude Code "Environment variables don't persist. An `export` in one command won't be available in the next." ([tools reference](https://code.claude.com/docs/en/tools-reference.md#what-persists-between-commands)); in INC-001 the agent relied on a `$HOME` it had set in an earlier call. In INC-803 the agent itself had restored `$HOME`, said so, and then deleted it; the reporter concludes that a delete target "should not depend on a mutable environment variable such as `$HOME`" ([anthropics/claude-code#93099](https://github.com/anthropics/claude-code/issues/93099)). In INC-030, a neighbour row in [pattern-matched boundaries](pattern-matched-boundaries.md), a cleanup trap expanded its variable at exit, after a later step had pointed it at `$HOME`. In each case the target was right when the agent last thought about it and wrong when it ran.

**An empty or wrong expansion widens the target instead of failing.** The shell expands a variable that is unset or empty to nothing, so a path built from it loses its first part; the class predates agents: a shipped launcher script ran `rm -rf "$STEAMROOT/"*` with the variable empty and deleted the user's files across the system ([ValveSoftware/steam-for-linux#3671](https://github.com/ValveSoftware/steam-for-linux/issues/3671), 2015). Inside double quotes the shell still runs command substitutions ([Bash manual, double quotes](https://www.gnu.org/software/bash/manual/html_node/Double-Quotes.html)), so a command meant as sample text runs for real (INC-801). A glob takes whatever matches in the directory the command runs in; INC-802 and INC-805 reconstruct such a delete under the home directory. A filter that does not apply leaves the full listing (INC-804).

**Cleanup is the step nobody watches.** The rows are teardowns, cache clears and test cleanups, steps at the end of a longer call or in a background task, after the work they serve is done. In INC-801 the delete ran in the background for about 21 seconds or more, by the report, before the agent noticed. The delete is also permanent where it lands: `rm` removes directory entries rather than moving them to a trash ([POSIX `rm`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/rm.html)), and the agent's own checkpoints do not cover shell deletes (the reversibility rungs in [Irreversible effects](irreversible-effects.md)).

**The record is often gone with the files.** In INC-802 no destructive command is in the session log, and INC-805 kept no session log at all. Both reporters reconstruct a glob delete from what survived: dot-entries such as `.DS_Store` remained, and a `*` glob skips dot-entries by default. That is the reporters' inference, and the rows are marked self-reported.

**Neighbours.** When the report puts the failure in a guard that read the command or path and let it through because it read the text, not what the text resolves to, the case is [pattern-matched boundaries](pattern-matched-boundaries.md): INC-030's permission check saw only `bash script`. This class is a delete whose resolved target nothing checked before it ran, whether or not a guard also read the text. INC-801 sits on that line: the reporter says permission checking ran, but not on the command that actually ran, and a commenter reads it as a check that cleared a command whose head was `python3` ([anthropics/claude-code#76208](https://github.com/anthropics/claude-code/issues/76208)); the report puts the failure in the substitution that built the target. INC-803's text says the session ran in [auto mode](https://code.claude.com/docs/en/permission-modes.md#eliminate-prompts-with-auto-mode), where a classifier reviews the actions that are not auto-approved (its form field says Accept Edits), and that report puts the failure in the target's design as well as in the missing detection. What the acting identity can reach, and when a person must approve an irreversible effect, is [Irreversible effects](irreversible-effects.md), which this doc does not restate. A wrong working directory because the agent assumed another environment is [world differs from assumed](world-differs-from-assumed.md) when the delete is incidental; when the delete is the damage, it is here. A delete the agent chose on purpose and aimed at the files it meant, such as INC-003, is not this class, and neither is a production resource the agent believed was staging (INC-006): there the target was chosen, not computed.

## Where it surfaces

At code, when the command runs: in every row cited here the deletion itself is the first sign, found by the person when folders are missing (INC-001), or announced by the harness errors that followed, a lost working directory and a sign-in prompt, before the person stopped the session (INC-803). In CI, when a cleanup script the agent wrote is committed: a shell linter would flag a delete built from a variable that can be empty (see the lint rung); none of the rows in Examples was caught that way, since none ran from a committed script. After merge, when a shipped script runs on a machine its author did not foresee, as the launcher script above did. The stages are spelled as in `docs/vocabularies.json`.

## Protections

The rungs are ordered by their own Cost lines, cheapest first: a default that costs nothing, a prompt rule, a few characters or lines at the delete site or one extra command before it, a tool to install, a CI job, a person's answer to each flagged delete, a model call per action, and last a sandbox and restorable state. The Tool defaults, Shell and Check rungs make the delete step fail closed; the others guide it, preview it, or catch it from outside. Limiting what the agent can reach and keeping its work restorable are the reach and reversibility rungs of [Irreversible effects](irreversible-effects.md); the last rung here only says where they break for this class.

### Tool defaults: let `rm` refuse the root and stay on one file system

- **Source:** [GNU `rm`](https://www.gnu.org/software/coreutils/manual/html_node/rm-invocation.html): `--preserve-root` is the default for a recursive delete, and `--one-file-system` skips directories on other file systems; [POSIX `rm`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/rm.html) also refuses an operand that resolves to the root directory.
- **Cost:** None for the default; one flag for `--one-file-system`.
- **Breaks when:** The target is anything but the root itself: `"$EMPTY/"*` expands to the root's children, not to `/`, and a home directory, a drive or a repository is not protected. `--one-file-system` does not help when the wrong target is on the same file system as the right one, as a home directory usually is.

### Prompt: name what a cleanup may delete, and have the agent delete by literal path

- **Source:** [Claude Code best practices](https://code.claude.com/docs/en/best-practices.md), which says a rules file is guidance and that "Claude is allowed to decide a guideline doesn't apply"; anything that must happen every time belongs in a hook, a deny rule or a managed setting.
- **Cost:** Context tokens in every session.
- **Breaks when:** The agent follows the rule in the text it writes and the text resolves elsewhere: in INC-803 the agent had just said the real `$HOME` was restored. A guideline can also be dropped as the session grows, and a rule the agent decides does not apply is not followed.

### Shell: make an empty or unset expansion fail instead of shrinking the path

- **Source:** The POSIX shell ([Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)): `${VAR:?}` writes an error and exits when the variable is unset or null, and `set -u` fails the expansion of an unset variable. [ShellCheck SC2115](https://www.shellcheck.net/wiki/SC2115) gives `${VAR:?}` as the fix for the launcher script's line. In Bash, `failglob` refuses to run a command whose glob matches nothing ([bash(1)](https://man7.org/linux/man-pages/man1/bash.1.html)). In PowerShell, [`Set-StrictMode`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/set-strictmode) refuses references to uninitialized variables.
- **Cost:** A few characters per expansion in a delete path, or one line per script.
- **Breaks when:** The variable is set and wrong. In INC-001 and INC-803 `$HOME` held a real path, so neither guard would have fired. `set -u` names only an unset variable, so one set to the empty string passes. `Set-StrictMode` version 1.0 exempts variables inside strings, which is how a path is usually built, and it holds only in the scope it is set in and its child scopes. An agent's one-off command carries a guard only if the agent writes it.

### Shell: stop when the step before the delete fails

- **Source:** [ShellCheck SC2164](https://www.shellcheck.net/wiki/SC2164): a `cd` that fails lets the script "keep going and do all its operations in the wrong directory"; the fix is `cd dir || exit`. `set -e` stops a script on a failed command ([Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)).
- **Cost:** A few characters per `cd`.
- **Breaks when:** The step before succeeds into the wrong place: a `cd` into a directory that exists but is not the one meant passes `|| exit`. POSIX ignores `set -e` in the condition of an `if` or `while` and in every member of an `&&` or `||` list but the last, and ShellCheck does not report SC2164 once `set -e` appears.

### Scratch: create the scratch directory once, and delete only the name it returned

- **Source:** [mktemp(1)](https://man7.org/linux/man-pages/man1/mktemp.1.html) creates a temporary directory safely and prints its name. Claude Code does not keep environment variables from one Bash call to the next by default ([tools reference](https://code.claude.com/docs/en/tools-reference.md#what-persists-between-commands)), so a delete in a later call has to name the returned directory as a literal, not carry it in a variable.
- **Cost:** One line per scratch directory, and a delete command that names it.
- **Breaks when:** The name is lost and the variable that should hold it is empty (combine with the expansion rung). The agent rebuilds the path from memory or from `$HOME` instead of the name it was given, as in INC-001 and INC-803, where the scratch space was a temporary `$HOME`.

### Preview: list what the delete would remove, and have the agent or a person read the list first

- **Source:** `git clean -n` shows what would be removed, and git refuses to clean without `-f` by default ([git-clean](https://git-scm.com/docs/git-clean)); rsync advises a `--dry-run` before `--delete` and caps deletions with `--max-delete` ([rsync(1)](https://download.samba.org/pub/rsync/rsync.1)); PowerShell's `-WhatIf` shows what the cmdlet would do without running it ([Remove-Item](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/remove-item)).
- **Cost:** One extra command and the time to read its output.
- **Breaks when:** The real run computes the target again and gets a different answer: a new Bash call without the variable (INC-001), another working directory, a variable changed in between. Nobody reads the preview; where a person is meant to, the rung is the show-the-plan approval rung of [Irreversible effects](irreversible-effects.md) and breaks as that rung does. A wildcard the shell expands before rsync sees it changes what `--delete` acts on. A filter can leave the full listing: in INC-804 `-Include` did not narrow a recursive Get-ChildItem listing, for a reason the report does not give, though the [Get-ChildItem](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-childitem) page recommends that form, `-LiteralPath` with `-Recurse` and `-Include`. A preview that trusts the filter misleads.

### Check: resolve the target, and refuse a delete outside the scope

- **Source:** [realpath(1)](https://man7.org/linux/man-pages/man1/realpath.1.html) prints the resolved absolute path, and `-e` requires that it exist; Python's [`Path.resolve()`](https://docs.python.org/3/library/pathlib.html) resolves symlinks. Comparing the resolved path with the directory a delete may clean, and stopping when it lies outside, is the check of the paths rung in [Pattern-matched boundaries](pattern-matched-boundaries.md), which sources it; here the delete step runs it on itself.
- **Cost:** A few lines per delete site, and someone has to define the scope.
- **Breaks when:** The comparison runs on the unresolved string: Python's `is_relative_to` is lexical, so a path with `..` in it passes. The allowed root is itself computed and wrong, for example a working directory that resolved to the home directory. The path changes between the check and the delete; that race is in the paths rung linked above. On platforms without fd-based functions, [`shutil.rmtree`](https://docs.python.org/3/library/shutil.html) can be led through a symlink during the delete.

### Trash: delete to a trash the person can restore from

- **Source:** [trash-cli](https://github.com/andreafrancia/trash-cli) moves files to the freedesktop.org trash from the command line; on Windows, .NET's [`DeleteDirectory`](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.fileio.filesystem.deletedirectory) can send a directory to the Recycle Bin, though its default is a permanent delete.
- **Cost:** Installing the tool, and disk space until the trash is emptied.
- **Breaks when:** The agent calls `rm` or `Remove-Item` instead of the trash tool, which nothing stops; trash-cli's own README advises against aliasing `rm` to it. trash-cli does not support Btrfs volumes, and .NET's Recycle Bin option is not supported in applications that are not user-interactive.

### CI: lint committed shell scripts for deletes built from expansions

- **Source:** [ShellCheck](https://www.shellcheck.net/wiki/SC2115) rules SC2115 (a delete under a variable that can be empty), [SC2114](https://www.shellcheck.net/wiki/SC2114) (a delete of a system directory, as from a stray space in a path) and SC2164 (above), run in CI or in the editor.
- **Cost:** A CI job, and its minutes on the pull requests that change a script.
- **Breaks when:** The delete never passes through a committed script. The five rows in Examples are commands the agent ran, not lines in a file, so a linter would not have seen any of them. Any ShellCheck rule can be switched off with a directive.

### Harness: let the agent's own check refuse deletes of critical paths

- **Source:** [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md): "Critical paths are the directories Claude Code protects from `rm` and `rmdir` commands, such as the filesystem root, your home directory, and your working directory." The page lists computed forms it flags as well, among them a glob directly under a variable that can be empty and a recursive delete whose target is only the output of a command substitution; for a glob or a trailing slash under a variable, the prompt says how to rewrite the command so the check passes.
- **Cost:** Built in; a person's answer to a prompt on each flagged delete.
- **Breaks when:** The [same page](https://code.claude.com/docs/en/permission-modes.md) says the check "can miss some commands, so it doesn't replace an operating-system control such as sandboxing", and that it covers only `rm` and `rmdir`. With the PowerShell tool on, `Remove-Item` gets its own, separate checks ([Remove-Item in PowerShell](https://code.claude.com/docs/en/permission-modes.md#remove-item-in-powershell)): system paths and wildcard targets are denied outright, and a recursive delete of the working directory or a parent goes through the mode's usual approval (the classifier in auto mode; `bypassPermissions` skips it). A per-file delete of files inside the workspace, the shape of INC-804 (a Codex incident), passes both. A wrong target that is not on the list, such as a sibling project, is not flagged. Launch-environment variables switch parts of the check off, among them `CLAUDE_CODE_DISABLE_SUBSTITUTION_RM_PROMPT` (a target that is only command substitution output), `CLAUDE_CODE_DISABLE_MOUNTED_DRIVE_RM_PROMPT` (the mounted-drive prompt) and `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` (the critical-path prompt in `bypassPermissions` mode). Where the check asks, it is the ask-at-the-tool-call approval rung of [Irreversible effects](irreversible-effects.md) and breaks as that rung does: a prompt approved without reading it. Elsewhere it denies rather than asks: in `dontAsk` mode; in auto and `bypassPermissions` modes when the terminal prompt's countdown runs out, and at once after three such timeouts; and away from the terminal, always in auto mode and in `bypassPermissions` mode unless a hook allows it.

### Classifier: block a delete whose target the reviewer cannot see

- **Source:** In Claude Code's auto mode the classifier blocks by default a recursive forced delete whose target is a shell variable "that isn't assigned anywhere in the conversation the classifier sees", and the block clears when the delete is re-run with the resolved literal path ([permission modes](https://code.claude.com/docs/en/permission-modes.md)). The classifier itself is the classifier rung of [Pattern-matched boundaries](pattern-matched-boundaries.md).
- **Cost:** A model call per action that reaches it, and some harmless deletes blocked.
- **Breaks when:** The variable was assigned earlier in the conversation, as in INC-001, where the agent set `$HOME` in one call and deleted it in a later one: the rule as written does not block that case, though the value no longer held. An independent stress test found that most misses on its cleanup task were in-project file edits, which skip the classifier (see Evidence).

### Reach and reversibility: confine writes to the workspace, and keep its work restorable

- **Source:** The reach and reversibility rungs of [Irreversible effects](irreversible-effects.md): a sandbox on the agent's shell, work kept in a remote repository, backups out of the agent's reach. For agent-scale rollback, a research filesystem holds an agent's changes until the user approves them and snapshots state so the agent can revert ([Zhong et al., YoloFS](https://arxiv.org/html/2604.13536)).
- **Cost:** As listed in that doc. For YoloFS the paper reports throughput matching Ext4, and a 4% overhead of its permission control on `stat` (as of 2026-09, Zhong et al.).
- **Breaks when:** The computed target is inside the reach the sandbox grants. A sandbox that allows writes to the working directory still lets a delete there take the repository's sources and part of its `.git` (INC-804), unless `.git` is protected separately, as Codex's `workspace-write` mode does ([Codex approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security.md)). INC-804 itself ran in Codex on Windows, and the report does not give the sandbox mode, so it does not show whether that protection held. A dev container's bind-mounted workspace is the host's folder, so a delete in it is a delete on the host ([Claude Code dev containers](https://code.claude.com/docs/en/devcontainer.md)). YoloFS is a Linux stackable filesystem its authors released as open source, not a packaged tool.

## Evidence

- A study of 290 public reports of coding agents misusing the filesystem found deletion in 39% of the 207 incidents and exploits in its impact summary (Figure 3); "42% of reports involve harm outside the project"; of the reports with known recoverability, 40% were unrecoverable; and where the agent's reaction is known, in 68% it carried on as if nothing had gone wrong (as of 2026-09, [Zhong et al.](https://arxiv.org/html/2604.13536)). These are counts of reports, not rates per session; no source found gives how often a destructive command occurs in normal use.
- An independent stress test of Claude Code's auto mode measured an end-to-end false-negative rate of 81.0% on 253 state-changing actions, with 36.8% of them outside the classifier's scope; the paper calls that share the Tier 2 coverage gap and finds it "most pronounced on artifact cleanup (92.9% FNR)" (as of 2026-10, [Ji et al.](https://arxiv.org/abs/2604.04978)). That task asks the agent to delete stale S3 artifacts in a simulated environment, and 49 of its 78 misses were Edit or Write calls on a state file, which auto mode does not send to the classifier. The authors attribute the difference from the vendor's own, lower figure (in [Irreversible effects](irreversible-effects.md)) to a different workload.
- Every incident cited here is a row in [`incidents/incidents.csv`](../../incidents/incidents.csv). Three of the class's rows, INC-800, INC-802 and INC-805, are self-reported: the destructive command is not in a log, and the mechanism is the reporter's reconstruction; they say so in the evidence-strength column. None of the class's rows comes from the maintainer's repositories.
