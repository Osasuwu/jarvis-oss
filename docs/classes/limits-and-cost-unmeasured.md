# Limits and cost unmeasured

## TL;DR

A limit on an agent's run or on the machinery around it (a turn cap, a timeout, a cost budget, a similarity threshold) holds a value that nobody measured, so it cuts off work that was going well, or lets bad work run on. A change merges whose cost to run (time, tokens, CI minutes) nobody measured, and the cost turns up later in someone else's run. Start by writing down what each limit's value rests on and putting cost in the acceptance criterion. Then record every run's turns, cost, duration and stop reason, give a limit that fires a stop reason of its own, and set its value from the measured runs that succeeded, in a unit the host's load does not change.

## Symptom

The agent's run stops at its turn limit with the task half done, and its log shows it was still making progress. Another run, on a harder task, spent every turn going round in circles, and the same limit let it. A CI job is killed at its timeout on a busy day and passes on a re-run, and nobody can say how long it usually takes. A hook (a script that runs before an agent's action and can refuse it) refuses a file because it is over a size cap that someone picked once, and the agent splits the file to get under it. A change merges, and the next week's token use, CI minutes or bill is twice what it was; the acceptance criteria never mentioned cost. A retry count or a quota fires far more often than anyone expected, or has never fired. Each limit is in plain sight in a config file. None has a measurement behind its value, so nobody knows how often it cuts off good work or lets bad work run on.

## Examples

Each `INC-` ID is a row in [`incidents/incidents.csv`](../../incidents/incidents.csv), which links its source, or marks it private, and says how strong that source is.

- INC-751: a worker agent made a one-line docs fix, its pull request passed every check and merged, and the workflow step that ran the agent still failed, because the agent took 51 turns and the cap was 40. The fix raised the cap to 100, about twice that one run.
- INC-757: a gate workflow capped its agent at 12 turns while its normal path takes about 13, so on every triggered run the agent was cut off before it posted its blocking comment, and the gate failed silently. The cap went to 20.
- INC-760: a smoke test's turn cap was cut from 10, in a pull request whose description calibrates it to one observed pattern of three turns. Caps of 2 and then 3 both failed, the merged value is 5, and the description still says 3.
- INC-752: an agent keeps notes between sessions in a memory store, each with a name, a type and a project. A hook refused a memory write whose similarity to a differently named memory of the same type and project reached 0.75, a cut-off set from two figures in its calibration note, one for paraphrases and one for related notes. It blocked a kind of write the note did not name, a scheduled daily snapshot about 0.98 similar to the previous one by design; the fix says it fired on every daily snapshot after the first, and a scheduled run found it.
- INC-755: a change that added a feature and turned it on by default made one pass of a pipeline about twenty times slower, from about 18 s to about 343 s. The slowdown was not explained or accepted when the change merged, and a bisect found the change about two weeks later (private, not verifiable).

## Mechanism

**A limit is a number someone picked, and a run is measured against it as if it were a fact.** Turn caps, timeouts, budgets and thresholds are set once, often from one run or a round guess, and then decide which runs count as failed. Work that is going well and work that is going nowhere look the same to the limit: both are a count that grew. Agent runs make the guess worse, because the same task does not cost the same twice: runs on one task "can differ by up to 30x in total tokens" ([Bai et al.](https://arxiv.org/abs/2604.22750)). Five forms appear in this class's rows.

**The value comes from one run or a guess.** A review workflow took its turn cap from one dry run of 28 turns times 1.5, giving 42; the next six runs went up to 57, and four of the six ended unreviewable on the cap (INC-750). A cap of 40 was raised to 100 as "~2x headroom" over one run of 51 turns (INC-751). A cap of 12 sat one turn under an estimated normal path (INC-757). A cap was doubled from 25 to 50 with no measurement cited in the pull request (INC-758). A reviewer's default of 5 turns was raised to 20, in a pull request whose title and description say 10 (INC-759). A cap was cut from 10 to 2 and then raised to 3 and to 5 in the same pull request, whose description still calls a cap of 3 calibrated to the "observed 3-turn" pattern (INC-760).

**Nobody knows what happens when the limit fires.** A limit can stop work that has already succeeded: in INC-750 and INC-751 the agent ended its session as a success after more turns than the cap, and the step failed anyway, because the count was checked after the run. A limit can stop the agent before its last action, so the run ends without its output: in INC-757 the run reported `error_max_turns` (the result an agent run ends with when it hits its turn cap), the blocking comment was never posted, and the gate failed silently. And a limit can hide what a check would have found: a nightly test meant to catch a change in a pipeline's number of passes or its stopping condition was killed at its 600 s timeout every night, and the issue that tracks that test, which INC-755's source links, says it would have fired on the change behind INC-755 if not for the timeout (private, not verifiable).

**A threshold that blocks was calibrated on the kinds of input someone thought of.** One row has this form. A hook that denies a write above a similarity score is a measuring instrument, and its cut-off is only as good as the cases it was set on. INC-752's 0.75 sat between two figures in its calibration note, about 0.79 for near-verbatim paraphrases and about 0.54 for related but distinct notes ([the hook](https://github.com/Osasuwu/jarvis/blob/64983e4b1eb918e908dbca7e0b0e3cd91c4db0cb/scripts/memory-dedup-check.py)). The note names no deliberate series of near-identical writes, and the hook blocked one, a daily snapshot written by a scheduled job. At about 0.98 that write is above any cut-off that still catches a paraphrase, so the fix exempted writes tagged as snapshots or as auto-generated and left the value at 0.75: the measurement that was missing was of the input, and no better value would have replaced it.

**Cost and speed are outside the acceptance criterion.** A change can do what it should and cost far more to run, and no check reads the cost. A change that added a feature and turned it on by default made a pipeline pass about twenty times slower (INC-755, private, not verifiable); a default flipped in another change took an integration test from about 42 s to 233.6 s. Under load, and slowed further by a thread leak, a separate defect, the test then ran past its 600 s timeout, so the main branch's CI was red on every push for two days (INC-754, private, not verifiable). A test fixture applied to every test slowed a suite from about 9 to 11 minutes to 25.2 minutes, past the CI job's 20-minute limit, so the job was killed on every pull request; the first diagnosis, a test hanging in native code, was refuted by a diagnostic run (INC-753, private, not verifiable). In performance pull requests, agents bring the measurement with them less often than human authors do: agent-authored ones include explicit performance validation in fewer cases than human ones, "45.7% vs. 63.6%" ([Peng et al.](https://arxiv.org/abs/2512.21757)).

**The limit is in a unit the host changes.** A wall-clock limit measures the host's load as much as the work. Stages of a search cut off by a wall-clock limit gave different results for the same code and the same input, depending on how busy the host was; a stage bounded by a count of evaluations reproduced bit for bit, 8 of 8 (INC-756, private, not verifiable). A timeout that a test meets on an idle runner it misses under load (INC-754, private, not verifiable).

**Where this class ends.** Here the limit is in plain sight and its value has no measurement behind it. In [silent fallback](silent-fallback.md), code catches a failure and carries on with a substitute, so the run looks healthy; INC-757 sits on that line, since the gate failed silently although its run reported `error_max_turns`, but it is here because the cause was a cap set under the work. In [proxy optimisation](proxy-optimisation.md), the agent trims or reshapes its work to fit a cap or a score: splitting a file to get under a size limit is that class, and the limit's value being a guess is this one. In [absence read as success](absence-read-as-success.md), a check never looked and its silence was counted as a pass; a capped run that a workflow counts as passed is that form, which a typed stop reason (below) makes visible, if something reads it. An agent that repeats edits without new information until a limit stops it is non-progressive iteration, a candidate class with no doc yet; there the limit is what ends the loop, and a turn cap is no cure for the loop itself.

## Where it surfaces

Most often in CI: 5 of this class's 11 dataset rows were caught there. It shows as a red step after a run that succeeded (INC-750, INC-751), as a job or a test killed at its timeout (INC-753, INC-754, both private, not verifiable), or as a cap changed three times inside one pull request (INC-760). In 4 rows it was found after merge: a gate that silently failed on every run (INC-757), a scheduled fixer that kept stopping at its cap (INC-758), a scheduled run that a hook blocked (INC-752), and a bisect of a slow pipeline about two weeks after the change merged (INC-755, private, not verifiable). In review, it shows when the reviewer agent runs out of turns before it posts its review (INC-759). At the task stage, it shows when a repeated run of the same work gives a different result (INC-756, private, not verifiable). Where a row states what a limit's value rested on, it was a handful of observations at most: one dry run (INC-750), one run that hit the old cap (INC-751), one observed pattern (INC-760), or two figures for two kinds of input (INC-752).

## Protections

Ordered from the cheapest rung to the strongest. The early rungs make the value and its basis visible; the later ones replace a guessed value with a measured one. No rung replaces another. A Source line that reads "one operator's practice" means the maintainer's practice, with no outside source behind it.

### Prompt and review: write each limit's basis beside it, and cost into the criterion

- **Source:** Anthropic's cost guide says to "establish a baseline before wider rollout" ([Claude Code costs](https://code.claude.com/docs/en/costs)); the .NET runtime team holds "no performance PR merges without empirical evidence, regardless of who contributes the PR" ([.NET Blog](https://devblogs.microsoft.com/dotnet/ten-months-with-cca-in-dotnet-runtime/)). A comment beside each limit naming the runs it came from, and a line on cost or speed in the acceptance criterion of a change that can move it, is one operator's practice.
- **Cost:** the time to write the basis, and tokens.
- **Breaks when:** the basis written is one run, which reads as a measurement: INC-751's fix calls its cap ~2x of a single 51-turn run, and INC-760's description calls a cap calibrated to one observed pattern. Or the text drifts from the value: INC-759's title says 10 and its diff sets 20, and INC-760's description says 3 and its diff sets 5.

### Record every run: turns, cost, duration and why it stopped

- **Source:** the Agent SDK returns an estimated `total_cost_usd` and per-model usage with each result ([Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). GitHub's team logged token use per agentic workflow run and found, in workflows already in production, "a 64-turn fallback loop" and a tool "called 342 times in one run" ([GitHub Blog](https://github.blog/ai-and-ml/github-copilot/improving-token-efficiency-in-github-agentic-workflows/)).
- **Cost:** storage per run, and someone who reads it.
- **Breaks when:** the record is not written on the run that hit the limit: in one GitHub Action, when the agent reached its turn cap, the file with the turn count and the cost "is never created" ([claude-code-action#1226](https://github.com/anthropics/claude-code-action/issues/1226)); or the figures are estimates, since the SDK's cost fields "are client-side estimates, not authoritative billing data" ([Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)).

### A limit that fires is its own stop reason

- **Source:** the Agent SDK ends a run that hits a cap with its own result subtype, `error_max_turns` or `error_max_budget_usd`, apart from `success` ([Agent SDK agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)). One project's design record splits the reason a run stopped from its status, after "A budget stop and an iteration cap were indistinguishable" ([nr-llm ADR-092](https://docs.typo3.org/p/netresearch/nr-llm/0.30/en-us/_sources/Adr/Adr092AgentRunTerminationReason.rst.txt)). An agentic-workflow tool fails the workflow when the agent stops at its cap, where before "no error is raised" ([gh-aw#2235](https://github.com/github/gh-aw/pull/2235)).
- **Cost:** a field per run, and code that reads it.
- **Breaks when:** the check runs after the agent finished, so a run that succeeded past the cap is reported as a failure (INC-750, INC-751); or the stop reason does not reach the decision it should change: INC-757's run reported `error_max_turns` on every triggered run, and the gate still failed silently, posting no blocking comment.

### A cost cap per run

- **Source:** the Agent SDK's `max_budget_usd` ([Agent SDK agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)); GitHub Copilot CLI's session limit, where "When the limit is hit, the agent stops cleanly and lets you know." ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit)).
- **Cost:** the run that the cap stops, and its partial work.
- **Breaks when:** the cap is checked after a response arrives, so one response overshoots it: the SDK compares spend with the cap "after model responses arrive" ([Agent SDK agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)), and a test with a cap of $0.01 ended at about $0.084 after one turn (as of 2026-04, [LinuxJedi](https://linuxjedi.co.uk/when-the-docs-fall-short-investigating-claude-codes-budget-cap/)); Copilot's limits are "soft limits" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit)); or the value is itself a guess, and the expensive runs are the ones that succeed. In one benchmark run, 20 of the 22 instances that cost more than $10 each were resolved (as of 2026-06, [OpenHands/benchmarks#741](https://github.com/OpenHands/benchmarks/pull/741)), so a $10 cap would have cut them.

### A blocking threshold runs in warn mode first

- **Source:** Kubernetes Pod Security Admission has `enforce`, `audit` and `warn` modes, and in `warn` "Policy violations will trigger a user-facing warning, but are otherwise allowed." ([Kubernetes](https://kubernetes.io/docs/concepts/security/pod-security-admission/)). Running a new blocking hook in warn mode, counting what it would block and reading a sample of it before it denies anything, is one operator's practice.
- **Cost:** a period in which the hook does not protect, and the time to read what it would have blocked.
- **Breaks when:** the warnings read cover only the kinds of write someone thought of. INC-752's calibration named paraphrases and related notes, and the write the hook went on to block was a third kind, a deliberate daily series that no cut-off on that score separates from a duplicate. A warn period that sees such a write shows that the hook needs an exemption by kind, not a new value; one that never sees it lets the block go live.

### Count the budget in a unit the host does not change

- **Source:** one operator's practice: bound each stage by a count of evaluations or turns, and keep a wall-clock limit only as an emergency stop whose firing means the stage did not finish, not a result. In INC-756 a stage bounded by a count of evaluations reproduced 8 of 8, while stages cut off by the clock did not (private, not verifiable).
- **Cost:** a counter in the code, and a wall-clock value still to set for the emergency stop.
- **Breaks when:** the emergency wall-clock limit is set as tight as the old one and becomes the limit again, so results depend on the host's load once more, as those of INC-756's clock-bound stages did (private, not verifiable). A count of turns also bounds the work, not the spend; the spend needs the cost cap above.

### Set the value from the measured distribution of runs that succeeded

- **Source:** on 100 SWE-bench Verified tasks, a turn cap at the 75th percentile of the uncapped runs' turns was a "sweet spot", "substantially reducing costs (by 24%-68%) with minimal impact on solve rates" across three models (as of 2025-11, [Gao and Peng](https://arxiv.org/html/2510.16786v2)). size-limit says "Add 25% to the current total size and use that as the limit" ([size-limit](https://github.com/ai/size-limit)); one CI change set each job's timeout from a table of observed durations: "Headroom is ~4× observed cold-cache durations" ([anthropics/buffa#19](https://github.com/anthropics/buffa/pull/19)). INC-750's second value, 1.5 times the largest of six measured runs, is one operator's practice.
- **Cost:** the runs to measure, with tokens and CI minutes for each; on the paper's three models a 75th-percentile cap changed the solve rate by −8.06% to +3.17% relative to no cap (as of 2025-11, [Gao and Peng](https://arxiv.org/html/2510.16786v2)).
- **Breaks when:** the sample is one run (INC-751, INC-760) or a few: INC-750's own pull request says its new cap "still undersells" a run that the first cap cut off at 43 turns, so its real need is unknown. Or the tail is heavy, and the expensive runs are the successful ones (the benchmark run in the rung above); or the task mix changes after the value is set.

### Measure cost and speed in CI against a baseline

- **Source:** github-action-benchmark compares each result with the previous one and alerts above a threshold that defaults to "200%" ([github-action-benchmark](https://github.com/benchmark-action/github-action-benchmark)); CodSpeed measures wall time and says "Walltime measures elapsed time, so it inherits the noise of the machine it runs on." ([CodSpeed](https://codspeed.io/docs/instruments/walltime)).
- **Cost:** CI minutes per run, and a benchmark per path that matters.
- **Breaks when:** the noise is as large as the change: on hosted runners "the amplitude of the benchmarks is about +- 10~20%" ([github-action-benchmark](https://github.com/benchmark-action/github-action-benchmark)); the check that runs the slowed path fails on its timeout instead of on the slowdown, so its red says the run was too slow for the limit and not by how much: INC-755's nightly test of the pipeline was killed at its 600 s timeout 16 nights in a row before a bisect tied the slowdown to its change (private, not verifiable); or the answer to a red benchmark is a bigger timeout instead of a cheaper change, which INC-754's issue ruled out in its own acceptance criterion (private, not verifiable).

## Evidence

- No study found measures this class directly: how often a limit set on an agent's run cuts off work that would have succeeded, or how often a merged agent change raises the cost of running it unnoticed (as of 2026-11, external search for this doc).
- In the SWE-agent paper, 93.0% of resolved instances were submitted before their cost budget ran out, against 69.0% of all instances (as of 2024-11, [Yang et al.](https://arxiv.org/html/2405.15793v3)); the authors read it as a sign that a larger budget would add little. A cap that rarely cuts off success can still cut off some.
- In SWE-smith, 53% of one model's failures (SWE-agent-LM-32b) are associated with run-time limits (cost, number of model calls, run time), while this "rarely happens with Claude 3.7 Sonnet" (as of 2025-05, [Yang et al.](https://arxiv.org/html/2504.21798)). The same limits cut one model's runs far more than another's.
- Runs on the same task "can differ by up to 30x in total tokens", and models predicting their own token use reach correlations of "up to 0.39" (as of 2026-04, [Bai et al.](https://arxiv.org/abs/2604.22750)). A value taken from one run carries that spread.
- A 75th-percentile turn cap cut cost by 24% to 68% across three models with a small change in solve rate, on 100 tasks (as of 2025-11, [Gao and Peng](https://arxiv.org/html/2510.16786v2)); the paper says repeating each experiment several times would be more robust than what it ran.
- Agent-authored performance pull requests carry explicit performance validation in 45.7% of cases, against 63.6% for human ones (as of 2025-12, [Peng et al.](https://arxiv.org/abs/2512.21757)).
- Most of the record is the maintainer's own: 7 of the class's 11 rows come from repositories the maintainer works in, 4 of them private. The rows are turn caps, timeouts, a similarity threshold and changes whose cost was not measured; no row is a size cap, a retry count or a quota, so what this doc says about those rests on the sources alone.
- Every incident cited here is a row in [`incidents/incidents.csv`](../../incidents/incidents.csv); four of the class's rows are private sources and say so in the link column.
