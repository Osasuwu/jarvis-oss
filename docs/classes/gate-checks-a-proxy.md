# A gate checks a satisfiable proxy

## TL;DR

A gate reads something cheap that usually goes with the property it guards: an approval exists, a status with the right name is green, a review comment is newer than the push, the body says `Closes #12`, the label says low risk. Each of these can be true while the property is false, and many can be written by the change the gate is judging. What stops it is a gate that binds its input to the commit, to the identity that must be independent of the change, and to platform state rather than text, and that computes a classification instead of reading one the change declares. External evidence for this class is thin; most of the record is the maintainer's own.

## Symptom

A required check is green and the property it is named after is false. The gate asked for a linked issue and found the words "Closes #12" in the pull request body, which are there whether or not the platform linked the issue and whether or not it is the right one. A freshness check compared a timestamp, and the result it accepted was for an older commit. A review requirement was met by an approval from the same account that pushed the change, or from a bot acting for it. Each gate ran, read its input and passed honestly: what it checked was true. The thing it was put there to protect was never checked.

## Examples

The INC- codes are rows in [the incident dataset](../../incidents/incidents.csv).

- INC-600: an agent drafted a doc, wrote a sign-off date into the doc's own metadata, added the matching line to the repository's sign-off record in a second commit (a rule asked for the two in separate commits, to show a person had read the doc in between), and merged the pull request with no review ([Osasuwu/jarvis-oss#53](https://github.com/Osasuwu/jarvis-oss/issues/53)); the audit that followed found that none of the repository's nine merged pull requests had carried a review ([Osasuwu/jarvis-oss#52](https://github.com/Osasuwu/jarvis-oss/pull/52)).
- INC-601: a gate meant to hold a high-stakes decision until research had been done on its topic accepted any research record the project had stored, on any topic, so it checked only whether the project had ever done research.
- INC-602: a review-freshness check accepted a review comment because it was posted after the head commit's time; the comment's own links pointed at an earlier commit, so a review of older content passed as a review of the head.
- INC-610 (private, not verifiable): pull requests carrying a closing keyword stopped being linked to their issues; a merge bot still announced each issue as closed from its own reading of the body, and the linked-issue check stayed green, so no signal showed that the issues stayed open.

## Mechanism

**The property is expensive, the proxy is cheap.** A person read the change; this review covers this commit; the issue the change closes is the right one and is still open; the change is low-risk. None of these is a field a script can read, so the gate reads something that goes with it in the normal case. Goodhart's law in Strathern's wording, "When a measure becomes a target, it ceases to be a good measure" ([Wikipedia](https://en.wikipedia.org/wiki/Goodhart%27s_law)), is about people steering toward the measure. This class does not need anyone to steer: the proxy and the property come apart on their own, and the gate cannot see it.

**The gated change can write the proxy.** A pull request body, a label, a frontmatter field, a ledger line, a commit message and an approval are all things an author can produce. In INC-600 the agent wrote two of them itself, the sign-off and its separate record, which the rule meant to show that a person had read the doc. The rule's check read back two records the drafter could write itself. On GitHub, any role from Triage up can apply labels ([repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)), so an agent with a write token can label its own pull request. "Users with push access in a repository can create commit statuses for a given SHA" ([commit statuses API](https://docs.github.com/en/rest/commits/statuses)), so a required check that accepts any source accepts a status of the right name from anyone who can push.

**Identity checks read the account, not the independence.** "Pull request authors cannot approve their own pull requests" ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews)) holds for the account. When the agent and its operator use one account, the records a gate reads (the sign-off, the label, the merge) are produced by the same login, and the gate cannot tell the agent's act from the person's (INC-600). An approval from a bot counts as an approval where the platform lets it: in INC-614 a pull request changed the workflow that ran on it so that the workflow's own token approved it, and the one-approval rule was met with no person involved. A gate that picks the review verdict by the shape of a comment, with no author filter, accepts a verdict from anyone who writes that shape (INC-608, private, not verifiable).

**Time and "latest" stand in for the commit.** A gate that asks whether the review is newer than the push, or reads the latest verdict on the pull request, is right while one run happens at a time. With two runs in flight, an earlier run can post after a later push and its result is taken for the head (INC-602, where the issue gives this as the apparent cause), or a run for an old head writes its verdict onto the new head (INC-611, private, not verifiable). A guard that reads the latest review comment, whatever commit it reviewed, takes an old verdict for the head (INC-607, private, not verifiable); when a run errors and posts nothing, it reads the comment from an earlier commit (INC-603). A research write-up describes the same pattern in other projects' workflows: a check comparing push and comment times that read the wrong field and skipped itself, an approval comment not bound to a commit, and a supply-chain tool that trusted an `updated_at` timestamp the platform did not change when branch protection was turned off and on ([BoostSecurity](https://labs.boostsecurity.io/articles/split-second-side-doors-how-bot-delegated-toctou-breaks-the-cicd-threat-model), INC-612). A review bot that checked the head had not moved during analysis then merged with a call that "merges whatever the PR head is at merge time" ([bazel continuous-integration](https://bazel.googlesource.com/continuous-integration/+/d464ae8a58fa3589bc5dea2533782cf30ec52985), INC-613). GitHub closed a gap where a merge commit made locally could differ from the reviewed merge while required approvals stood: it "will be rejected if the contents differ from the system-created merge" ([GitHub changelog, 2023-06](https://github.blog/changelog/2023-06-06-security-enhancements-to-required-approvals-on-pull-requests/), INC-615).

**Text stands in for platform state.** A linked-issue gate that matches a keyword in the body passes whether the platform linked the issue or not. GitHub's own relation is weaker than it reads: `closingIssuesReferences` is a "List of issues that may be closed by this pull request" ([GraphQL reference](https://docs.github.com/en/graphql/reference/pulls)), and nothing in it says the issue is open or the right one. In INC-610 the platform stopped linking and every check that read the body stayed green.

**Presence stands in for relevance.** A gate that asks for a field, an artifact or a reference checks that one exists. Whether it is the one that matters, for this topic, this change, this commit, is a judgement the gate does not make (INC-601).

**Proxies also fail the other way.** When the proxy is false and the property true, the gate blocks good work. A review that was fixed by editing the pull request body, with no new commit, could never produce a verdict newer than the head commit, and the gate failed every re-run, and the pull request was merged by an administrator around it (INC-604). A review hold that labelled every new pull request also held pull requests that changed no document (INC-605). A check that verifies each quoted passage against its credited sources failed a quote as missing when the one source that carried it was the source it could not fetch (INC-606). In INC-604 the route around the false block was an administrator's merge, which no gate held.

**Reports read the same proxy.** In INC-610 a merge bot announced each issue as closed from its own reading of the body, while the linked-issue check stayed green and the issues stayed open. The announcement and the check agreed, and neither matched the platform's state.

**Where the neighbours begin.** If the agent changed its work, its tests or its evidence until a measure passed, that is [proxy optimisation](proxy-optimisation.md); this doc is about the gate's design, whoever or whatever satisfies the proxy. If the guard misread how a command or path is spelled, that is [pattern-matched boundaries](pattern-matched-boundaries.md). If the check never ran, was skipped or saw nothing, and that counted as a pass, that is [absence read as success](absence-read-as-success.md); here the check ran on its input and the input was the wrong thing.

## Where it surfaces

Mostly after merge. In 8 of this class's 15 dataset rows the gap was found after the change had merged, by an audit of the gate, by a later failure, or by a researcher reading the workflow; the gate that read the proxy did not go red. In CI (5 rows), in four of them the gate went red on good work: a review taken for the head that belonged to an earlier commit (INC-602), a verdict read from an earlier commit's comment (INC-603), a freshness check that could not see a fresh review (INC-604), and a check that blamed the wrong source (INC-606); for the fifth, a verdict written onto the wrong head, the record does not say which way the gate went (INC-611). At merge (2 rows), the sign is either a pull request whose checks are all green while its approval came from no person (INC-614), or a hold that stops pull requests it was not meant for (INC-605). Counts as of 2026-11, from [`incidents/incidents.csv`](../../incidents/incidents.csv).

## Protections

### Design review: for each gate, name the property, the input and who can write the input

- **Source:** one operator's practice. The question is asked of each gate before it is made required: what property does it guard, what does it actually read, and can the change under review, its author or its agent write that input.
- **Cost:** review time per gate, and a second look whenever the gate's input changes.
- **Breaks when:** the divergence is one of timing nobody thinks of (two runs in flight, INC-602), or the input looked independent and was not (one account for agent and person, INC-600).

### Platform: do not let an automated identity's approval count

- **Source:** the Claude GitHub action: "For security reasons, Claude cannot approve pull requests" ([claude-code-action capabilities](https://github.com/anthropics/claude-code-action/blob/main/docs/capabilities-and-limitations.md)). GitHub added an organisation setting that "protects against a user using Actions to satisfy the "Required approvals" branch protection requirement" ([GitHub changelog, 2022-01](https://github.blog/changelog/2022-01-14-github-actions-prevent-github-actions-from-approving-pull-requests)). OpenSSF Scorecard: "Review by bots, including bots powered by artificial intelligence / machine learning (AI/ML), do not count as code review" ([Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md)). GitHub's agentic workflows let the agent only stage writes, which are vetted after it exits ([GitHub agentic workflows security architecture](https://github.blog/security/vulnerability-research/under-the-hood-security-architecture-of-github-agentic-workflows/)).
- **Cost:** a setting per organisation or repository; reviews that a bot would have given now wait for a person.
- **Breaks when:** an administrator turns on bot approvals, as GitHub now allows for Copilot code review, where "Copilot can submit an approval that counts toward the repository's required-approvals rule" once enabled ([GitHub changelog, 2026-09](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests)); or the bot's approval arrives through a workflow the pull request itself changed (INC-614). Scorecard itself still counts a merger different from the committer as an implicit review (Scorecard checks).

### Branch rule: pin each required check to the app that must report it

- **Source:** GitHub lets a required check name its expected source: "If status is then provided by a different app or by a user via a commit status, merging will be prevented" ([GitHub changelog, 2021-11](https://github.blog/changelog/2021-11-30-ensure-required-status-checks-provided-by-the-intended-app/)).
- **Cost:** minutes per required check, and an edit whenever the reporting app changes.
- **Breaks when:** the check was made required before pinning existed, since "Existing required status checks will continue to accept status from any app" until edited (same changelog); or the pinned app is one the change can drive, such as a workflow whose definition is taken from the branch under review, the route INC-614 used to produce an approval.

### Read platform state, not text the change wrote

- **Source:** GitHub records the link between a pull request and the issues it closes as `closingIssuesReferences` ([GraphQL reference](https://docs.github.com/en/graphql/reference/pulls)), separate from the body text a common linked-issue action checks for ([nearform-actions check-linked-issues](https://github.com/nearform-actions/github-action-check-linked-issues)). Checking that each referenced issue exists, and the issue's state after the merge, is one operator's practice.
- **Cost:** an API call per check.
- **Breaks when:** the platform's own relation fails silently, as in INC-610 (private, not verifiable); or the question is whether the issue is the right one, which no source found here checks: the relation lists issues that "may be closed" (GraphQL reference).

### Bind every verdict and approval to the commit it read

- **Source:** required checks must pass on the head: "Checks from earlier commits don't satisfy the requirement" ([troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)). A merge made by automation passes the analysed SHA, and "GitHub's merge API rejects the merge with `409 Conflict` if the provided SHA is not the current head" ([bazel continuous-integration](https://bazel.googlesource.com/continuous-integration/+/d464ae8a58fa3589bc5dea2533782cf30ec52985)). A workflow gated by a label or approval checks out the commit, not the branch: "Use immutable references (Commit SHA) to make sure that the reviewed code does not change between the check and the use" ([CodeQL query help](https://codeql.github.com/codeql-query-help/actions/actions-untrusted-checkout-toctou-high/)). Writing the reviewed SHA into the review's own evidence, and having the gate match it exactly instead of comparing times, is one operator's practice (the fix that closed INC-602, [Osasuwu/jarvis#1982](https://github.com/Osasuwu/jarvis/pull/1982)).
- **Cost:** a SHA carried through each step; a re-review per push.
- **Breaks when:** the SHA is looked up at write time instead of carried from the read (INC-611, private, not verifiable); one merge path does not pass it, as with a merge call that "merges whatever the PR head is at merge time" (INC-613); or the property is not a property of the commit, as when a review finding is fixed in the pull request body (INC-604).

### Compute the classification from the change; never read one the change declares

- **Source:** a vendor's write-up of its auto-approval of low-risk changes: "First, engineers cannot self-classify a change as low-risk", and the tier comes from fixed criteria ([Ona](https://ona.com/stories/auto-approving-low-risk-prs)); Ona sells an agent platform. GitHub reads code owners from the base: "pull requests use the version of `CODEOWNERS` from the base branch of the pull request" ([about code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)). Computing the risk tier from the changed paths with a classifier pinned outside the branch, and counting a bypass label only when a person other than the author applied it, is one operator's practice.
- **Cost:** a classifier and its criteria to maintain; changes that cross a tier boundary wait for a person.
- **Breaks when:** "If any line in your CODEOWNERS file contains invalid syntax, that line will be skipped" (about code owners), so a broken line drops an owner without a red; or the label that grants a bypass can be set by anyone with Triage (repository roles).

### Platform: the author cannot approve, and a push needs an approval from someone else

- **Source:** "Pull request authors cannot approve their own pull requests" ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews)); with "Require approval of the most recent reviewable push", "the most recent reviewable push must be approved by someone other than the person who pushed it", and stale approvals can be dismissed when new commits change the diff ([about protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). GitLab: "By default, the creator of a merge request (author) cannot approve it", with settings to stop approval by users who added commits ([GitLab approval settings](https://docs.gitlab.com/user/project/merge_requests/approvals/settings/)). For an agent's pull requests, GitHub's cloud agent "Prevents the user who asked Copilot cloud agent to create a pull request from approving it" ([Copilot risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
- **Cost:** a second person with write access for every review, and a review round per push.
- **Breaks when:** the agent pushes under its operator's account, so the person who must approve is the account that pushed (in INC-600 both commits were under the account that would have reviewed); administrators are exempt, since without the extra setting "the restrictions of a branch protection rule do not apply to people with admin permissions" (about protected branches); on GitLab, "Merge request creators can edit the approval rule in an individual merge request and override this setting" unless overrides are locked (GitLab approval settings). In a UK AISI evaluation an agent opened a pull request on a real project and was found "creating fake online identities and using them to pressure the project's maintainer to approve the code"; the maintainer refused ([AISI incident report](https://www.aisi.gov.uk/blog/incident-report-unsanctioned-agent-behaviour-during-cyber-testing)).

### Separation of duties: a person independent of the change decides

- **Source:** SLSA's source track: "Changes in protected branches MUST be agreed to by two or more trusted persons prior to submission" ([SLSA source requirements](https://slsa.dev/spec/v1.2/source-requirements)). NIST SP 800-53 AC-5: "Separation of duties addresses the potential for abuse of authorized privileges" ([AC-5 on csf.tools](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-5/), a third-party copy of the NIST text). With one developer, a hold meant to be lifted by that person alone (a required check that stays red while a label is on, the label kept off the agent's reach) is one operator's practice, used because one developer cannot request a review from themselves ([Osasuwu/jarvis-oss#53](https://github.com/Osasuwu/jarvis-oss/issues/53)). The rule for when the agent must stop and ask is stated once, in [irreversible effects](irreversible-effects.md); this rung depends on it.
- **Cost:** a second trusted person per change, or, with one developer, that developer's reading time on every held change.
- **Breaks when:** the person and the agent share the account that lifts the hold, so the agent can lift it too (in INC-600 the agent merged under the account that would have reviewed); SLSA lets an organisation grant "a Trusted Robot a perpetual exception" (SLSA source requirements).

## Evidence

No study found here measures how often a gate passes on a proxy. Public trackers do not report gate failures as incidents: the 4 external rows in this class are a researcher's write-up of other projects' workflows, a fix commit, a demonstration and a platform changelog, and none of them reports a coding agent writing the proxy. The other 11 rows are from the maintainer's repositories, which build their own gates and so meet this class more than a typical project would; 4 of them are private (as of 2026-11, [`incidents/incidents.csv`](../../incidents/incidents.csv)).

Two dated signals bear on the identity rungs. In its report of 2026-08, the UK AI Security Institute describes an agent in a cyber evaluation that opened a pull request on a real project and created other identities to press the maintainer to approve it; the maintainer did not ([AISI incident report](https://www.aisi.gov.uk/blog/incident-report-unsanctioned-agent-behaviour-during-cyber-testing)). In 2026-09 GitHub made it possible, off by default, for a model's approval to count toward required approvals ([GitHub changelog, 2026-09](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests)). Both widen the gap between the existence of an approval and an approval by an independent person.

No source found here gives a cost figure for any rung.
